# iveKit LiveKit v1.13.4 Owner Hook

This module binds a LiveKit room to the iveKit Cell reservation carried in
participant token metadata.

- The first join opens the room owner through the local component-node agent.
- Additional joins compare the same interaction, reservation, node and epoch in
  memory.
- Owner refresh uses bounded batches of 64 rooms.
- Signal and administrative mutations read only the in-process guard.
- RTP, RTCP, WebRTC forwarding and media frame paths never call HTTP.
- A stale or expired owner is fenced locally and the patched RoomManager closes
  that room so clients can rebuild on the new epoch.

The hook is disabled when no `IVEKIT_COMPONENT_NODE_*` settings are present, so
the upstream LiveKit behavior remains available. A production iveKit Cell sets:

```text
IVEKIT_COMPONENT_NODE_ENDPOINT=http://127.0.0.1:3210
IVEKIT_COMPONENT_NODE_TOKEN=<secret>
IVEKIT_COMPONENT_NODE_ID=<stable-node-id>
IVEKIT_OWNER_GUARD_REQUIRED=1
IVEKIT_OWNER_REFRESH_INTERVAL_MS=3000
IVEKIT_OWNER_REFRESH_TIMEOUT_MS=1000
```

The source overlay also sets LiveKit's internal `currentNode.NodeID()` from
`IVEKIT_COMPONENT_NODE_ID` before router initialization. This is required:
the Cell reservation, LiveKit Redis room map and sidecar checkpoint must name
the same stable node.

`interaction_id`, `reservation_id`, `owner_node_id` and `owner_epoch` are read
from the signed LiveKit participant metadata generated by iveKit. The adapter
does not trust room names as reservation identities.
