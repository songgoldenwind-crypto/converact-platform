## 1. 隔离方式

本轮没有覆盖或重启服务器现有 `led-platform`、`ivekit-app`、`ivekit-media`。验证资源全部使用独立名称：

- 目录：`/opt/ivekit-v2-validation/c15dfb4`
- 镜像：`ivekit-service:c15dfb4`
- 容器：`ivekit-v2-service-c15dfb4`、`ivekit-v2-postgres-c15dfb4`
- 网络：`ivekit-v2-validation-c15dfb4`
- 数据卷：`ivekit-v2-postgres-c15dfb4`
- HTTP：仅绑定 `127.0.0.1:18300`，没有新增公网入口

数据库管理员密码和 runtime 密码均在服务器本地随机生成，只写入权限为 `600` 的验证环境文件；报告、Git 和命令输出不记录凭据。

| 检查项 | 结果 |

| migration 数量 | 30 |

本轮使用一次性管理员迁移容器执行 `dist/ivekit-migrate.js`，长驻服务只使用 `opc_runtime`。迁移 runner 持有 advisory lock、记录 checksum，并在发现已应用 migration 内容漂移时 fail closed。

## 4. 服务启动验收

独立镜像以 `opc_runtime` 连接 fresh database，关闭本轮未接入的 provider worker 后成功启动：

```json
{"ok":true,"postgres":true}
```

服务日志没有 `FATAL`、数据库 permission error 或 RLS error。日志中的 Redis、LiveKit、Tinode、AI 配置缺失均为本轮刻意未接入 provider 的预期 warning，不代表对应能力已完成 V2 重验。

验收结束时服务器仍有约 6.1 GiB available memory，根磁盘使用率 17%。现有 LED 五个容器和昨日 iveKit application/media 容器均保持运行，healthcheck 容器仍为 healthy。

## 5. 验证过程发现的问题

首次执行时，临时验收脚本通过 heredoc 向 `docker exec` 发送授权 SQL，但遗漏 `-i`，SQL 未进入 psql，runtime 查询因此得到 `permission denied for table collaboration_sessions`。增加 `docker exec -i` 后，从全新卷完整重跑通过。该问题只存在于临时验收脚本，不在 iveKit 迁移或运行镜像中。
