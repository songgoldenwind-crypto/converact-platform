# 通信底座技术升级与开源扩展审计

> 审计日期：2026-07-22
> 审计范围：OPC 与 LED 共用的 iveKit 通信底座
> 审计对象：IM、SIP/语音、音视频、屏幕共享、录制、远控、通知、文件安全、内容智能、共享数据与部署运维
> 基线文件：`docs/architecture/communication-technology-baseline-v1.json`
> 状态：架构裁决完成，第一批运行时与依赖升级已落地；其余按本文分阶段实施

## 1. 结论

当前底座不是“从零开始”，也不是“已经生产完成”。更准确的状态是：

1. 通信功能与抽象边界基本成型，已经具备继续深挖源码和横向扩展的基础。
2. RustPBX、LiveKit、Tinode、RustDesk、Kamailio 都已经形成 iveKit 自己的控制、审计、容量或热路径补丁，不能简单替换后重写一遍。
3. 当前主要问题不只是版本旧，还包括组件缺失、生产交付漂移、单副本依赖、可观测性断层、供应链不可复现，以及“设计拓扑”和“正式 Chart/Compose”不完全一致。
4. 因此本轮不是单纯升级当前组件，而是同时执行三条路线：
   - **升级**：把适合继续使用的组件升级到受支持版本并重放 iveKit 补丁。
   - **替换**：对停止维护、技术路线已迁移或当前组件不再合适的部分进行替换。
   - **扩展**：新增当前底座缺少、但能实质改善性能、扩展性、可观测性或完整功能的开源项目。
5. 不采用“项目越多越先进”的做法。每个新增项目必须回答五个问题：解决什么问题、放在哪一层、是否进入实时热路径、引入多少服务、如何回滚。

本次形成 46 项技术裁决，其中包括升级、替换、新增、POC、延后和明确拒绝。机器可校验基线由：

```bash
npm run verify:technology-baseline
```

进行验证。

## 2. 不变的架构目标

### 2.1 容量目标

平台按照单套多节点可横向扩展至十万并发的标准设计，但日常业务不依赖十万并发才能成立。优化顺序是：

1. 先把单节点的 CPU、内存、网络、文件描述符、端口、队列和锁竞争利用到合理上限。
2. 再验证从 1 节点扩到 2、4、8 节点时，每增加一台服务器得到的有效容量是否接近线性。
3. 只有现有内核、协议栈或组件被性能剖析证明为瓶颈时，才引入 RTPEngine、Cilium、DPDK、QUIC/RoQ 等更重方案。
4. 单机密度、横向扩展效率和故障域隔离同时成立，不能靠把全部组件堆在一台机器上换取表面上的“服务器更少”。

### 2.2 热路径不变量

以下链路不得同步依赖 PostgreSQL、对象存储、ClickHouse、OCR/ASR、LLM、Webhook、邮件、审计查询或远程控制面 HTTP：

- SIP INVITE 与事务重传；
- RTP/RTCP 转发；
- LiveKit SFU packet forwarding；
- Tinode 单条消息 fanout；
- RustDesk relay 数据转发；
- WebSocket 心跳和既有会话的 owner 路由。

录音上传、视频 Egress、文件转码、病毒扫描、OCR、ASR、翻译、AI 质检、指标导出和审计持久化必须使用有界队列、独立 worker、超时、熔断和降级。它们失败时可以丢失非关键副本、进入重试或隔离，但不得中断正在进行的电话、视频或远控会话。

### 2.3 组件引入规则

新增组件只有满足以下条件才进入默认生产路径：

1. 当前已有明确缺口，不能仅凭“更新、更热门”引入。
2. 不和现有组件重复拥有同一份业务或会话 authority。
3. 有明确的容量维度、健康检查、drain、故障语义和 SLO。
4. 镜像必须锁定 digest，源码 fork 必须锁定 40 位 commit。
5. 能在旧路径旁路验证，并具备配置级或流量级回滚方案。

## 4. 代码与交付审计结果

### 4.1 P0：立即处理

#### P0-1 Node 23 已结束维护

审计时根服务、standalone 服务、容量运行时和多个 CI job 使用 Node 23。Node 23 已结束维护，不应继续作为生产基线。

本轮已经完成：

- 根 `Dockerfile` 改为 `node:24-bookworm-slim`；
- `services/ivekit-service/Dockerfile` 构建和运行阶段改为 Node 24；
- `infra/capacity/Dockerfile` 改为 Node 24；

- 六个 GitHub Actions workflow 统一到 Node 24。

本机目前仍运行 Node 23.11，因此本地 npm 会提示 engine warning；CI 与交付镜像才是权威运行环境。后续开发机也应切到 Node 24。

#### P0-2 Nodemailer 直接依赖存在高危漏洞

审计前根项目与 standalone 包直接依赖 Nodemailer 6.10.1。`npm audit --omit=dev` 报告高危任意文件读取/SSRF 和地址解析 DoS 等问题。

#### P0-3 RustDesk Server 1.1.16 安全 rebase

当前 fork manifest 已切换到 `1.1.16@73523b31cfd25d77dee862e6fc9f5e1fb5e485ef`。1.1.16 包含未经认证的 UDP punch-hole 反射/放大修复及运行时修复。当前证据是：

#### P0-4 MinIO 已不适合作为未来自建生产基线

当前生产 Compose 在 `infra/docker-compose.production.yml:104` 固定了 2025 年 MinIO 镜像。MinIO 上游仓库已经归档，不能继续把它当成长期维护的自建对象存储。

处理原则：

- 立即保留现有 S3 provider 接口，不让业务代码依赖 SeaweedFS 私有 API；
- 云环境优先使用供应商 S3；
- 必须自建时用 SeaweedFS 做兼容 POC；
- MinIO 只保留短期开发/迁移读取能力，不再新增依赖；
- 迁移前验证 multipart、版本、加密、对象锁、生命周期、Egress 和证据链；
- 存储故障继续与活动通信 fail-open 隔离。

#### P0-5 “production” Compose 仍有浮动镜像和开发配置

`infra/docker-compose.production.yml` 存在以下问题：

- `postgres:16-alpine`：第 7、23、40 行；
- `redis:7-alpine`：第 83 行；
- `nats:2-alpine`：第 95 行；
- LiveKit/SIP/Egress 使用可变 tag：第 158、171、185 行；
- Kamailio 仍是 5.8：第 208 行，与自建 6.0.7 不一致；
- RustDesk 旧默认 1.1.15 已改为必填的批准仓库 digest 引用；
- Kong 3.8 使用 tag：第 400 行；
- Chatwoot 使用 `latest`：第 670 行；
- PostgreSQL、Redis、NATS、MinIO、Keycloak 等管理端口被直接发布；
- Keycloak 使用开发启动模式且存在默认管理凭据 fallback；
- Redis/NATS 缺少完整 TLS、认证和集群合同。

因此该文件当前更接近“完整功能联调 Compose”，不能继续命名或宣传为生产 HA 交付。后续应拆成：

1. `compose.dev`：允许本地依赖，端口只绑定 loopback；
2. `compose.acceptance`：固定镜像，供单机服务器验收；
3. `helm/production`：仅消费外部 PostgreSQL、Valkey、NATS、S3 等生产合同。

### 4.2 P1：进入下一批开发

#### P1-1 正式 Root Chart 仍包含多个单副本状态组件

以下模板不能代表生产高可用：

- PostgreSQL：`infra/k8s/templates/postgres-statefulset.yaml:8`；
- Redis：`infra/k8s/templates/redis-deployment.yaml:7`；
- NATS：`infra/k8s/templates/nats-statefulset.yaml:16`；
- LiveKit：`infra/k8s/templates/livekit-deployment.yaml:43`；
- LiveKit SIP：`infra/k8s/templates/livekit-sip-deployment.yaml:9`；
- RustDesk：`infra/k8s/templates/rustdesk-server-deployment.yaml:22`；
- MinIO：`infra/k8s/templates/minio-deployment.yaml:25`。

处理方式不是简单把 `replicas` 改为 3，而是把状态组件外置，并为每个通信组件补入口、owner、drain、故障和恢复合同。

#### P1-2 Standalone Chart 的 Tinode 仍为单副本

`services/ivekit-service/helm/ivekit/values.yaml:534` 默认 Tinode 副本为 1，PVC 为 RWO。该模板适合开发和受控验收，不能证明 Tinode 集群生产完成。

必须补充：

- 至少三副本 StatefulSet 与稳定 node ID；
- 原生 cluster discovery 与 peer 认证；
- client Service 和 cluster Service 分离；
- readiness 同时检查 Tinode、PostgreSQL、owner lease；
- drain 时先拒绝新连接，再释放 topic owner；
- reconnect 后按 durable sequence 补消息；
- fanout、cluster RPC、store、reconnect storm 指标。

#### P1-3 LiveKit 生态缺 Ingress

当前已经有 Server、SIP、Egress，但没有 LiveKit Ingress。缺少它意味着外部摄像机、OBS、RTMP、WHIP、HLS/MP4 输入只能另写转码服务。

建议新增 LiveKit Ingress v1.5.0，单独作为高 CPU worker pool：

- RTMP 与 WHIP 入口独立暴露；
- Redis 与 LiveKit 使用专用凭据和 keyspace；
- 按 RTMP/WHIP/transcode 类型建立容量单位；
- KEDA 根据 pending job 与 worker 可用容量扩容；
- Ingress 故障不得影响既有 LiveKit 房间；
- LED 可通过 iveKit API 创建、查询、更新和删除 ingress，不直接依赖上游 API。

#### P1-4 缺少 SIP 级可观测性

当前 Kamailio 与 RustPBX 有 Prometheus 指标，但指标只能回答“多少错误”，不能回答“一次呼叫在哪个事务、哪个节点、哪个响应分支出错”。

建议新增 HOMER 11 + HEP：

- Kamailio 使用 `siptrace` 将 HEP3 异步复制到 collector；
- 默认不写 Kamailio 本地 trace 数据库；
- 支持按租户策略、错误码、采样率或临时诊断开关采集；
- 发送队列有上限，collector 不可用时丢弃追踪副本并计数，不影响 SIP；
- Call-ID 在 HOMER 内使用，导出和长期保存前执行号码/身份字段治理；
- HOMER 负责 SIP call flow，OTel 负责 HTTP/worker/DB 跨服务 trace，两者通过 interaction/correlation ID 关联，不互相替代。

当前实施状态：Kamailio `siptrace`/HEPv3 connector、Compose/Helm 配置、默认关闭、禁止本地 trace DB、OPTIONS/KDMQ 过滤和 NetworkPolicy collector CIDR 约束已完成。HOMER 11.0.297 collector 的不可变镜像部署、按 Call-ID 的确定性采样、drop/queue 指标、PII 保留策略落地和 collector 故障压测仍未完成，因此不能把 HOMER 标记为生产验收完成。

#### P1-5 NATS 代码与部署合同已完成，目标集群证据待运行

废弃的 `nats@2.29.3` 已从容量运行时移除。当前统一使用
`@nats-io/transport-node`、`@nats-io/nats-core` 和 `@nats-io/jetstream` 3.4.0，
普通事件 publisher、容量 dispatcher 和容量 worker 共用同一连接配置解析器：

- URL 不允许携带凭据，也不允许混用 TLS 与明文节点；
- 用户名/密码、token 和 mTLS 使用互斥且完整的配置合同；
- connect timeout、reconnect wait、attempts 与 jitter 有界；
- publisher 合并并发 connect，不对每条消息执行 flush，关闭时 drain；
- 容量命令流显式要求 `1|3|5` 副本，本地受控 Compose 固定为 1，生产 Kubernetes 固定为 3；
- 已存在的 JetStream stream/consumer 若副本、subject、retention、storage、ack、redelivery 或背压配置不一致会 fail closed；
- 生产 NATS 模板为三节点、每 Pod 独立 RWO PVC、client/route mTLS、认证、PDB 和拓扑分散。

受控测试、TypeScript 编译、Compose/Kubernetes YAML 解析及 NATS 配置语法校验已通过。
尚未运行的是目标 Kubernetes 上的三节点重启、网络分区、leader 切换、stream restore、
consumer redelivery、证书/凭据轮换和故障期间媒体连续性证据，因此状态是
`implemented-not-run`，不是生产验收完成。

#### P1-6 缺完整 OpenTelemetry 链路

RustPBX lockfile含 OTel 依赖，但应用层没有统一 W3C trace context、Collector 和采样策略。新增方案：

1. iveKit HTTP、NATS/JetStream message、Provider 调用、PostgreSQL outbox worker 使用统一 trace/correlation context；
2. Node、Go、Rust 和 Python SDK 只做边界 span，不对每个 RTP 包、每个 SFU 包或每个 fanout recipient 建 span；
3. Batch exporter 使用有界内存和超时；
4. Collector 不可用时 fail-open；
5. 低基数指标继续走 Prometheus，trace 只做采样；
6. PII 不写 attribute，interaction ID 使用不可逆内部 ID。

#### P1-7 CI 与依赖供应链还不可完全复现

- GitHub Actions 多数仍使用 `actions/*@v4` 等 tag，而不是 commit SHA；HOMER 与 RustPBX 镜像链已改为 full-commit pin；
- Rust workflow 使用 `dtolnay/rust-toolchain@stable`；
- Go workflow 未固定完整 patch toolchain；
- `services/ai-agent-py` 已改为 exact direct requirements，并生成完整传递依赖 lock；`services/speech-host/requirements-funasr.txt` 等其余 Python 服务仍需按同一规则收敛；
- 仓库级 Renovate 策略、fork 上游发现索引、镜像 digest 与 Action SHA pin 规则已实现并通过配置校验；实际 GitHub App 运行和首批 PR 仍为 `not_run`；
- 已实现 digest-only 的统一 Trivy SPDX/漏洞、Cosign keyless 签名和 GitHub provenance/SBOM attestation 门禁，并接入 HOMER、RustPBX、LiveKit SIP 和 RustDesk Server；Registry 运行证据和其余镜像接入仍未完成。

建议把供应链作为正式功能，不作为文档附录。

### 4.3 P2：分阶段偿还

#### P2-1 TypeScript 严格模式债务

根、standalone 与 capacity tsconfig 都是 `strict: false` 和 `skipLibCheck: true`：

- `tsconfig.json:8`；
- `services/ivekit-service/tsconfig.json:8`；
- `infra/capacity/tsconfig.json:8`。

全仓一次开启 strict 会产生大量旧 OPC 业务域错误，不应借通信升级做大爆炸重构。建议新增严格子项目：

1. communication contracts；
2. provider adapters；
3. placement/capacity；
4. notification/file workers；
5. 新增代码必须进入 strict project。

#### P2-2 根 Dockerfile 仍在生产运行 TypeScript

根 `Dockerfile` 仍安装 devDependencies，并以 `tsx src/server.ts` 运行，没有 `USER node`。standalone Dockerfile已经采用 build/prune/non-root，是正确方向。

后续应：

- 新建 production tsconfig；
- 只编译服务运行需要的 source graph；
- runtime image 只带 production dependencies；
- non-root + read-only filesystem；
- 配置生成和临时文件写入显式 volume；
- 不把测试、脚本、SDK 源码全部带入运行镜像。

#### P2-3 Fork 仍全部未达到 production eligible

fork manifest 中 RustPBX、rsipstack、LiveKit、Egress、SIP、Tinode、RustDesk Client/Server 都是 `production_eligible: false`，例如第 443、568、722、936、1058、1148、1347、1527 行。

这是正确的诚实状态。不能因为单元测试、补丁应用或单机 SIPp 通过就改成 true。每个 fork 至少要具备：

- exact source + lockfile + immutable image；
- SBOM、漏洞结果和 provenance；
- 升级/回滚演练；
- 真实多节点故障、drain、长稳与容量证据；
- 对应协议的真实链路，而不是只测 HTTP fake。

### 6.3 仅做 POC，不默认引入

#### RTPEngine

RTPEngine 适合：

- 运营商 NAT 与媒体锚定；
- RTP/SRTP/ICE 协议互转；
- 统一媒体策略、DTMF、转码或旁路录制；
- RustPBX 原生媒体达到瓶颈后的数据面拆分。

它不应默认处理每一路媒体，因为会增加一次网络跳、双份端口预算、媒体节点与 B2BUA 的会话一致性问题。首先完成 RustPBX 原生 V1/V2/V3 媒体基准，再用同一硬件 A/B。

#### Centrifugo

可用于 OPC 控制事件、通知和 presence fanout，但不能和 Tinode 同时拥有聊天消息、topic 和 durable sequence。只有非聊天 WebSocket fanout 成为瓶颈时才引入。

#### Cilium/Hubble

适合平台级 eBPF 网络可观测性和策略，但属于 CNI 迁移，不是应用依赖。必须由集群平台单独 POC，尤其验证 hostNetwork、UDP、NodePort 和 LiveKit/RustDesk 路径。

#### SIPhon

SIPhon 的 Rust SIP proxy/B2BUA、Python policy、HEP、RTPengine、SIPREC 与热加载设计值得对标，但当前 Kamailio 与 RustPBX 已分别拥有 Edge 和 B2BUA authority。它只进入同服务器、同 SIPp workload 的性能与故障 POC；除非在 CPS、active dialog、P99 setup、重传正确性和运维成本上证明显著优势，否则不引入第三套 SIP authority。

#### 未来自建智能 Provider（当前不选型）

iveKit 不把某个 OCR、ASR、TTS 或模型推理引擎写死在业务层。当前只交付 Provider gateway、协议适配、治理和媒体隔离；未来是否自建、采用哪个运行时，必须在真实模型、硬件、准确率、TTFT、吞吐、成本和恢复测试之后单独决策。AI 服务过载只允许影响字幕、翻译、机器人或质检副本，不得影响活动通信。

### 6.4 明确拒绝或延后

- 不用 OpenSIPS 重做当前 Kamailio 能力，除非实测 Kamailio 达不到 frontier。
- 不再引入 Jitsi、Janus、mediasoup 与 LiveKit 重复拥有 SFU。
- 不在 RTP/SFU 热路径放服务网格 sidecar。
- 当前不加 Kafka/Redpanda，除非 JetStream 在保留量或吞吐上被实测击穿。
- 当前不为共享通信底座引入 Temporal；outbox + JetStream 足够承载现有异步流程。
- 当前不默认上 Ceph；对本项目“更少服务器”目标过重。SeaweedFS 先验证。
- DPDK、QUIC/RoQ、kernel bypass 只在 profile 证明瓶颈后进入实验。
- 不引入 CCS-CallReport 的 PHP/MySQL 代码；仅把有价值的报表字段纳入 iveKit PostgreSQL/ClickHouse 投影。
- 不整套引入 AVA 或 Pipecat 作为第二机器人运行时；其低延迟、frame、barge-in 与取消机制在 LiveKit Agents 内实现。

## 7. 目标架构

```text
Users / Devices / Carriers
          |
          +---------------- HTTP/WSS ----------------+
          |       Existing HTTP Edge / Ingress       |
          |                                          v
          |                          iveKit API / SDK / Webhooks
          |
          +---------------- SIP ---------------------+
          |       L4 -> Kamailio Edge (2+/Cell)      |
          |            |                    |         |
          |            | HEP async          |         |
          |            v                    v         |
          |         HOMER 11            RustPBX pool  |
          |    sip-exporter passive        |          |
          |                                  |         |
          |                      optional RTPEngine A/B|
          |
          +------------- WebRTC / TURN ---------------+
          |   L4 -> LiveKit Signal/SFU pool            |
          |          |        |         |              |
          |       Ingress   SIP pool  Egress pool      |
          |
          +---------------- IM ------------------------+
                  L4 -> Tinode cluster

Cell-local control:
  component admission + owner epoch + signed snapshots + drain state

Shared off-hot-path platform:
  CloudNativePG / PostgreSQL 18
  Valkey cluster
  NATS 2.14 JetStream
  external S3 or SeaweedFS
  ClamAV + FFmpeg workers
  Provider Registry / Gateway
    -> external OCR
    -> external batch + realtime ASR
    -> external translation / TTS / Model Gateway
  OTel Collector + VictoriaMetrics + HOMER

Deferred threshold / benchmark lanes:
  ClickHouse asynchronous analytics projection
  future platform HTTP edge migration
  optional cluster-network/eBPF POC
  future self-hosted intelligence providers
```

### 7.1 Cell 内原则

- 每个 Cell 自己完成新会话 admission，不跨 Region 同步请求后再接通。
- Kamailio、RustPBX、LiveKit、Tinode、RustDesk 使用稳定 node identity 和 owner epoch。
- 状态型实时会话不宣称透明迁移；节点故障时按协议真实能力重连、重建或结束。
- placement 快照与配置快照本地读取；控制面短时故障不影响已建立会话。
- 每个 Cell 能独立 drain，扩缩容不直接删除仍有 owner 的节点。

### 7.2 更少服务器的实现方式

“服务器越少越好”不等于所有组件单副本：

- VictoriaMetrics 先使用高密度 single-node，而不是一开始部署 Mimir 全家桶；
- HOMER 11 可从 all-in-one 起步，超过 ingest/retention 阈值再拆 writer/node/coordinator；
- NATS 同时承担 event bus 和 JetStream，不另加 Kafka；
- PostgreSQL/Tinode/iveKit 可共享运维集群，但数据库、角色、连接池和容量预算隔离；
- 外部 S3 优先于自建大量存储节点；确需自建才部署 SeaweedFS；
- AI/OCR/ASR worker 可共用 GPU 池，但调度、显存预算和模型实例独立。

## 10. 验收标准

### 10.1 每个组件

- exact source/image identity；
- 配置 schema 与启动前校验；
- readiness、liveness、drain；
- bounded queue、timeout、circuit breaker；
- 低基数 metrics、SLO、alert、runbook；
- 单节点性能曲线；
- 2/4/8 节点扩展效率；
- 节点、网络、依赖、磁盘和下游故障注入；
- rollback 与数据兼容；
- SBOM、漏洞、provenance。

### 10.2 通信链路

- SIP：真实 SIPp + RTP，不以 reject-only signaling 代替媒体容量；
- Video：真实 publisher/subscriber、TURN、丢包、弱网、reconnect、Egress/Ingress；
- IM：真实 WebSocket、durable ACK、编辑删除、附件、重连补偿；
- Remote：两台 Windows、键鼠、剪贴板、文件、多屏、录屏、断开与完整审计；
- Storage：上传中断、multipart resume、对象存储全停时活动通信继续；
- AI：Provider 超时、熔断、降级、切换，不能影响原始消息/媒体。

### 10.3 状态名称

统一使用：

- `implemented`：代码和静态合同已完成；
- `controlled_pass`：受控自动化通过；
- `real_environment_pass`：真实环境通过；
- `capacity_pass`：指定硬件和 workload 通过；
- `production_eligible`：全部 release、故障、恢复、安全和运维门禁通过。

禁止用 `implemented` 推导“生产完成”，也禁止用单机 signaling CPS 推导媒体并发。

## 13. 最终裁决

当前底座可以继续作为 OPC 与 LED 的共用底座，不需要推倒重来；但接下来的工作绝不能只做版本升级。

正确路线是：

1. 保留并深改已经掌握的 RustPBX、Kamailio、LiveKit、Tinode、RustDesk；
2. 立刻补 HOMER、LiveKit Ingress、OpenTelemetry 和供应链能力；
3. 用 CloudNativePG、Valkey、SeaweedFS 修正状态层和存储层的长期路线；
4. 当前只接外部 OCR、实时/批量 ASR、翻译、TTS 和 Model Provider；不在当前三波选择或部署任何自建智能运行时；
5. 任何进入实时数据面的新组件都先做同硬件 A/B，特别是 RTPEngine、独立 TURN、Cilium 和 QUIC；
6. 以单节点密度、横向扩展效率、故障恢复和生产证据共同作为完成标准。
7. 以端到端 RTC QoE 和弱网恢复作为容量通过的共同门槛；连接数达标但体验门槛失败时整场结果为失败。

这份审计和机器基线共同构成后续开发的技术准绳。任何新组件、替换或重大版本升级，都应先更新基线决策、验收门槛和回滚方案，再进入默认生产路径。
