# NATS JetStream HA Deployment

## 1. Scope

NATS carries Converact Fabric control events and bounded asynchronous work queues. It never carries SIP,
RTP, WebRTC packets, Tinode fanout payloads, RustDesk frames, or recording bytes. An unavailable
NATS cluster may delay events and workers, but it must not terminate or degrade an established
call, video room, IM connection, or remote-control stream.

## 2. Supported Topologies

| Environment | Nodes | Stream replicas | Purpose |
| --- | ---: | ---: | --- |
| controlled Compose | 1 | 1 | code, restart, and redelivery development only |
| production Cell/Region | 3 | 3 | normal production baseline |
| larger production Region | 5 | 3 or 5 | only after capacity and failure-domain evidence |

Production uses an odd quorum. Each NATS Pod owns a separate `ReadWriteOnce` volume; shared NFS,
one PVC mounted by every Pod, and host-local ephemeral JetStream storage are unsupported. Pods are
spread across zones and hosts, and the PDB preserves a voting majority.

## 3. Authentication And TLS

The root Kubernetes chart expects two externally managed Secrets:

- client/route authentication Secret: `client-user`, `client-password`, `route-user`,
  `route-password`;
- TLS Secret: `ca.crt`, `tls.crt`, `tls.key`.

Capacity runtime examples use `converact-capacity-runtime` keys `nats-url`, `nats-user`, and
`nats-password`, plus `converact-capacity-nats-tls` keys `ca.crt`, `tls.crt`, and `tls.key`.
Passwords must not be embedded in a NATS URL. Route credentials appear in route URLs generated by
the server template and therefore must use URL-safe random characters.

Certificates must cover the client Service, headless Service, and stable StatefulSet pod DNS
names. Clients set `NATS_TLS_MODE=required`, verify the CA, and present their certificate and key.
Credential and certificate rotation must be rehearsed with overlapping trust before production.

## 4. JetStream Contracts

The capacity dispatcher requires `CONVERACT_FABRIC_CAPACITY_NATS_STREAM_REPLICAS` explicitly. Supported
values are `1`, `3`, and `5`; production templates set `3`. It fails closed when an existing stream
does not match the expected subject, work-queue retention, file storage, maximum age, or replica
count. Durable consumers similarly verify filter subject, explicit ACK, ACK wait, maximum delivery,
and `max_ack_pending` pressure bounds.

Application publishers do not flush after each message. Connections are coalesced, reconnect waits
are jittered, and shutdown drains the connection. PostgreSQL outbox/checkpoint state remains the
authority for recoverable workflows; JetStream redelivery is not treated as exactly-once execution.

## 5. Failure Isolation

1. Media and realtime message forwarding never synchronously wait for NATS.
2. Failed event publication returns a bounded failure and leaves recovery to the outbox or caller.
3. Capacity workers checkpoint generator output before evidence uploads or terminal ACKs.
4. Slow consumers have bounded pending limits; overload is rejected or retried instead of growing
   process memory without limit.
5. NATS, PostgreSQL, object storage, scanners, and Provider workers use independent resource pools.

## 6. Required Production Evidence

Before production acceptance, execute and archive:

1. three-node bootstrap, leader election, rolling restart, one-node loss, and zone loss;
2. network partition with majority and minority behavior recorded;
3. durable consumer ACK, NAK, redelivery, poison-message termination, and slow-consumer pressure;
4. stream snapshot/restore to a clean cluster and object-count/hash reconciliation;
5. client reconnect P50/P95/P99 and duplicate/ordering observations;
6. client and route credential rotation plus CA/certificate rollover;
7. disk high-water, full-volume, corrupted-member replacement, and restore runbook;
8. concurrent live SIP/LiveKit/Tinode/RustDesk sessions proving NATS loss does not interrupt their
   data paths.

Repository tests, TypeScript compilation, manifest rendering, and NATS configuration parsing are
controlled evidence only. The target Kubernetes failure, restore, rotation, and media-continuity
matrix is currently `not_run` and must not be reported as production-passed.
