# iveKit 服务器部署验收报告

> 验收日期：2026-07-11
> 服务器：`64.225.122.227`，Ubuntu 24.04，4 CPU，7.8 GiB 内存
> 验收范围：LiveKit Media Core、Egress/MinIO、OPC facade、PostgreSQL/RLS、Tinode、RustDesk OSS、LED SDK 对接
> 结论：后端通用底座和真实服务器链路达到第一版可集成状态；RustDesk 物理客户端操作仍需桌面端人工验收。

## 1. 部署拓扑

iveKit 使用两个独立 Compose project：

- `ivekit-media`：Caddy L4、LiveKit、Redis、Egress、MinIO。
- `ivekit-app`：OPC、PostgreSQL、Redis、Tinode、RustDesk `hbbs`/`hbbr`。

公网入口：

- `wss://livekit.64-225-122-227.sslip.io`
- `turns://turn.64-225-122-227.sslip.io:443`
- `https://opc.64-225-122-227.sslip.io`
- `wss://tinode.64-225-122-227.sslip.io/v0/channels`

所有域名均使用 Let's Encrypt 可信证书。PostgreSQL、两个 Redis、MinIO API/Console、LiveKit 内部信令端口和 TURN 内部端口未公开。服务器原有 `led-platform` 五个容器在部署、重启和恢复测试期间未被重启或替换。

## 3. 本轮发现并修复的问题

1. macOS tar 上传产生 `._*.sql` AppleDouble 文件，迁移器误当 SQL 执行。现只接受 `NNN_lowercase_name.sql`。
2. 服务启动 Promise 未捕获，数据库失败时进程曾以 0 退出。现启动失败明确记录 `FATAL` 并退出 1。
3. `PoolClient` 被误识别成 `Pool` 后重复 `connect()`。事务助手现复用已连接 client。
4. 独立 Tinode 数据库被空库预创建，官方初始化无法接管。现由 Tinode 官方 initializer 创建 schema。
5. Tinode 服务账号缺少幂等 bootstrap。现启动前创建或登录验证。
6. 应用原先使用 PostgreSQL 超级用户，FORCE RLS 可被绕过。现拆分迁移账号和运行账号。
7. HTTP 请求虽解析租户头，但异步 Store 未共享 tenant GUC。现整个路由使用同一租户事务/PoolClient。
8. RustDesk 签名 launch 页没有租户头，RLS 下误报 404。现仅在签名校验成功后按 external ID 做受限 bypass 查询。
9. HTTP JSON parser 忽略 DELETE body，结束会话丢失 `actor_identity`。现支持 DELETE JSON body。
10. RustDesk 证据脚本把 `host:port` 当 DNS host。现探针提取主机，客户端配置保持原样。
11. 独立栈遗漏 RustDesk protocol URL template。现提供可拉起客户端的默认模板。
12. Tinode 用户名、密码超过 PostgreSQL adapter 限制。现用户名为最多 26 字符并带稳定哈希，密码固定 32 字符。
13. Tinode 对账号或 topic 权限幂等 no-op 返回 304，客户端误报失败。现按操作语义处理 304。
14. 双实例竞争创建 chat binding 返回唯一约束 500。现使用 `ON CONFLICT DO NOTHING` 并读取胜者。
15. 8 张遗留租户表仅由运行期构造器建表且无 RLS。现纳入 migration 031，191/191 tenant table 强制 RLS。
16. 运行账号重复执行 DDL，权限错误被忽略。现 migration-managed 模式跳过旧构造器 DDL，`exec()` 的其它错误不再静默吞掉。
17. JWT 篡改测试偶发接受非规范 Base64URL 尾字符。根因是不同字符串可被宽松解码为同一签名字节；现 JWT 三段要求 canonical Base64URL，避免令牌字符串不唯一影响审计、撤销和缓存语义。
18. OPC/Tinode 长驻容器持有 `opc_admin` 凭据。现迁移改为 `postgres-migrate` 一次性服务，OPC 只持有 `opc_runtime`；Tinode 使用独立 `tinode_app` 和独立数据库权限。
19. 旧 RLS policy 只信任任意会话均可设置的 `app.bypass_rls` GUC。现运行账号无法开启通用 bypass；登录、注册、签名 RustDesk launch 查询和后台队列发现改为固定用途、撤销 PUBLIC 权限的 `SECURITY DEFINER` 函数。
20. 多 OPC 实例冷启动可能并发执行迁移，且运行账号曾能修改迁移账本。现整轮迁移持有 PostgreSQL advisory lock，默认只由一次性迁移服务执行，并在每次迁移后撤销 `opc_runtime` 对 `schema_migrations` 的全部权限；服务器并发迁移 2/2 成功，账本四种 DML 权限均为 false。
21. Tinode 短用户名规范化后可能碰撞，但直接换算法会割裂已有账号。现新账号用户名始终包含原始 `tenantId + identity` 的稳定哈希，同时先用旧算法登录回退；服务器复用真实旧账号后 Basic 账号数量未增加。
22. MinIO 根凭据曾直接交给 OPC/Egress。现根账号只用于 bootstrap，OPC/Egress 使用限定 `recordings` 桶的 service account；服务器验证该账号可读写对象但管理员 API 被拒绝，根/业务 access key 或 secret 相同时 bootstrap 会失败。
23. 数据库密码直接拼接 URL，特殊字符可能破坏 DSN。现 OPC 使用离散 `PGHOST/PGDATABASE/PGUSER/PGPASSWORD`，Tinode 使用无密码 DSN 加 `PGPASSWORD`；配置测试覆盖 `@:/#%`。

## 4. 恢复与基础性能

`ivekit-app` 执行 `down` 后重新 `up`，未删除 named volume。恢复后 OPC/Tinode 公网均为 200，数据和 RustDesk key 保持。Media Core 五个长驻服务重启后 LiveKit 为 200，Egress/MinIO healthy，录制对象哈希不变。

低强度并发结果，不等同正式压测：

| 探针 | 请求/并发 | 成功 | P50 | P95 | Max |
| --- | ---: | ---: | ---: | ---: | ---: |
| OPC public health | 100/10 | 100 | 17.3 ms | 127.7 ms | 207.1 ms |
| authenticated chat capabilities | 50/10 | 50 | 21.0 ms | 69.5 ms | 76.7 ms |
| LiveKit TLS ingress | 50/10 | 50 | 17.4 ms | 94.0 ms | 113.8 ms |

探针结束后 OPC 约 147 MiB，PostgreSQL 41 MiB，Tinode 17 MiB，LiveKit 18 MiB，Egress 18 MiB，两个 Redis 各约 3 MiB；日志未出现 FATAL、panic、worker failure、RLS permission error。

代码交付门禁 `npm run verify` 最终为 1818 项测试、1814 通过、4 项按预期跳过、0 失败；TypeScript 类型检查及 Go、Python、Rust 侧车检查全部通过。服务器上的真实 PostgreSQL RLS 集成测试再次执行为 6/6 通过，真实注册/登录为 201/200，LED SDK 再次完成 Media + IM 调用。

## 6. 对 LED 研发的结论

LED 可按 `iveKit HTTP SDK -> OPC facade -> LiveKit/Tinode/RustDesk` 的方式接入，不应直接访问 PostgreSQL，也不应让浏览器绕过 OPC 发布业务消息。业务消息必须经 facade 落库和 policy scan 后再投递 Tinode。RustDesk 客户端连接字段由 client-config/launch-plan 下发，操作事件回传同一 audit/timeline。详细接口仍以 [iveKit 视频、远程协助与 IM 通用能力详细设计](converact-fabric-video-im-capability-design.md) 和 [LED integration guide](converact-led-integration-guide.md) 为准。
